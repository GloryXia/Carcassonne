# 规则引擎技术设计

- 文档版本：0.1
- 状态：建议设计
- 目标：可测试、可回放、可扩展且与渲染完全分离

## 1. 边界

规则引擎负责：

- 规则集和地块池准备
- 确定性随机与抽取
- 地块合法性、旋转和放置
- 区域拓扑、完成状态和控制权
- 角色放置与回收
- 基础及扩展计分
- 回合状态机和终局
- 产生可解释的领域事件

规则引擎不负责：

- 手机和 3D UI
- 网络连接、设备身份和重连
- 数据库事务
- 动画、音效和 AR
- 房主权限和防火墙

## 2. 处理模型

```text
GameState + RuleCommand + Ruleset
  → Validate
  → Decide
  → DomainEvents
  → Apply Events
  → New GameState
```

- `Validate` 返回稳定错误码，不改变状态。
- `Decide` 不执行 I/O，不读取系统时间。
- `Apply` 是事件到状态的唯一正式变更路径。
- Host 在数据库事务中保存事件和新状态修订号。

## 3. 回合状态机

建议状态：

```text
NotStarted
  → Setup
  → TurnStarting
  → AwaitingTilePlacement
  → AwaitingPieceAction
  → ResolvingEffects
  → ScoringCompletedFeatures
  → TurnEnding
  → FinalScoring
  → Finished
```

### 3.1 自动阶段

`TurnStarting`、`ResolvingEffects`、`ScoringCompletedFeatures`、`TurnEnding` 和 `FinalScoring` 由引擎自动推进，直到需要玩家选择或游戏结束。

### 3.2 玩家阶段

- `AwaitingTilePlacement` 接受地块位置和旋转选择。
- `AwaitingPieceAction` 接受角色放置、扩展替代动作或跳过。
- 扩展秘密选择使用显式的 `AwaitingChoice` 子状态或选择队列，不用 UI 临时变量表示。

客户端不能提交“确认分数”。分数由权威规则自动产生。

## 4. 核心类型

### 4.1 稳定 ID

为下列对象定义不同的强类型 ID：

- `GameId`
- `RulesetId`
- `PlayerId`
- `SeatId`
- `TileDefinitionId`
- `TileInstanceId`
- `PieceInstanceId`
- `SegmentInstanceId`
- `FeatureComponentId`
- `ChoiceId`

规则核心内部 ID 使用种子与单调计数器产生，不调用 `crypto.randomUUID()`，也不读取进程级随机源。

### 4.2 网格

```text
BoardPosition = (int X, int Y)
Rotation = North | East | South | West
Direction = North | East | South | West
```

多格和半格地块将来通过 `FootprintCell` 和离散子单元扩展，不改用浮点坐标。

### 4.3 GameState

至少包含：

- 规则集 Manifest 与内容哈希
- 当前状态修订号
- 玩家顺序和玩家状态
- 当前回合和当前阶段
- 已放置地块
- 地块池顺序和随机状态
- 区域图与角色位置
- 待处理效果和玩家选择
- 分数与计分记录
- 终局和胜利结果

## 5. 地块定义

地块定义使用数据表达：

- 外形和占用子单元
- 允许旋转
- 边缘端口
- 内部区域段
- 内部连接
- 修道院、花园等中心特征
- 盾徽和扩展符号
- 可选角色热点的语义区域
- 放置约束元数据

示意结构：

```text
TileDefinition
  id
  footprintCells[]
  rotations[]
  segments[]
    localSegmentId
    featureType
    boundaryPorts[]
    symbols[]
  internalConnections[]
  centerFeatures[]
  placementTags[]
```

具体 JSON Schema 在逐块目录录入前单独冻结。

## 6. 区域拓扑

### 6.1 源数据结构

使用显式 `FeatureGraph` 作为事实来源：

- 节点是放置后实例化的地块区域段。
- 边表示地块内部连接或相邻地块端口连接。
- 角色、符号和开放端口附着在节点或组件上。

### 6.2 连通缓存

基础游戏的连接单调增长，可以使用并查集加速组件合并。但并查集不能成为唯一事实来源，因为未来扩展可能改变连接、桥梁、渡口或区域状态。

推荐：

- 图结构是可重建的权威拓扑。
- 并查集或组件索引是派生缓存。
- 动态规则使缓存失效时，从图局部重建组件。
- 快照可以保存组件索引，但加载时验证其与图一致。

### 6.3 组件 ID

区域合并时不能让客户端依赖任意内存地址。建议：

- 每个新段获得稳定 `SegmentInstanceId`。
- 组件的规范 ID 由规则定义的稳定算法产生。
- 合并事件明确记录旧组件到新组件的映射。
- 计分事件保存实际参与的段和地块，即使之后组件被归档。

## 7. 合法地块位置

算法步骤：

1. 收集所有已放置地块正交相邻的空位置。
2. 枚举地块允许的非等价旋转。
3. 对每条已有邻边比较端口类型和扩展约束。
4. 检查外形重叠、河流回折和特殊地块规则。
5. 返回排序稳定的合法 `(position, rotation)` 列表。

结果排序必须固定，例如先 `Y`、再 `X`、再旋转枚举值，不能依赖哈希集合迭代顺序。

## 8. 角色合法性

放置角色时：

1. 命令必须处于允许的回合阶段。
2. 角色属于当前玩家并位于供应中。
3. 目标段位于本回合刚放置的地块。
4. 目标段允许该角色类型。
5. 查询完整连接组件中的现有角色和扩展限制。
6. 产生角色放置事件或稳定拒绝错误。

热点坐标只用于 UI 命中，规则命令使用语义 `localSegmentId`。

## 9. 区域完成

### 9.1 道路

统计组件所有道路开放端口；每个端口必须连接或由规则定义的终点关闭。

### 9.2 城市

组件不得存在未连接的城市边界端口。

### 9.3 修道院和花园

检查中心位置周围八个整数坐标是否均被有效地块覆盖。

### 9.4 田野

基础规则中田野不在游戏中按完成计分；最终计分时根据组件邻接的已完成城市集合处理。

## 10. 控制权与计分

计分分成：

- `FeatureFacts`：组件地块、符号、角色、开放端口和邻接对象
- `ControlResult`：每位玩家有效力量和获胜者集合
- `ScoreBreakdown`：基础项、修正项、最终分与规则来源
- `ScoreAwarded`：写入玩家分数的领域事件

UI 只展示 `ScoreBreakdown`，不重复实现公式。

基础策略：

- 道路计分器
- 城市计分器
- 修道院/花园计分器
- 最终未完成区域计分器
- 田野计分器

扩展通过明确的计分贡献接口修改事实或添加修正项，不覆盖整个基础计分器。

## 11. 规则模块

建议的 TypeScript `RuleModule` 接口能力：

- 声明模块 ID、语义版本和依赖
- 贡献准备阶段组件
- 贡献地块放置约束
- 贡献角色动作和选择
- 贡献阶段处理器
- 贡献控制权力量
- 贡献计分修正
- 贡献最终计分
- 贡献协议可见的规则说明

模块顺序由 Ruleset Manifest 显式列出并生成哈希。禁止依靠依赖注入容器的发现顺序。

## 12. 确定性随机

- 不使用 `Math.random()` 或第三方库的隐式全局随机源。
- 选择并冻结一个适合 TypeScript 的明确算法，例如以四个 `uint32` 保存状态的 xoshiro128**。
- 实现固定的种子、状态转移和测试向量。
- 洗牌使用固定的 Fisher–Yates 实现。
- 快照保存完整 PRNG 状态，而不只保存初始种子。
- 随机抽取事件保存结果，重放时不重新随机。

升级随机算法需要新的规则版本，旧录像继续使用旧算法。

## 13. 确定性编码规则

- 规则使用整数、枚举和定点值，不使用浮点位置。
- 所有普通数值必须保持在 JavaScript 安全整数范围；协议解码时拒绝 `NaN`、无穷和非整数规则值。
- 32 位算法的每步都使用 `>>> 0` 等明确方式归一化；溢出行为由算法规范和测试向量定义。
- 不依赖本地时区、系统文化或系统时钟。
- `Object`、`Map`、`Set` 和数据库查询得到的集合在参与事件或哈希前稳定排序。
- 核心状态不保存 UI 文本，只保存语言无关代码。
- 规则内容使用 UTF-8 和规范化字段。
- 状态指纹使用专门的规范序列化，不直接哈希普通 `JSON.stringify()` 输出。
- 确定性测试必须在 Node.js 24 的 WSL2 Linux、Windows x64 和 CI 环境运行同一黄金向量。

## 14. 状态指纹

每个提交后的状态生成 SHA-256 指纹。规范输入至少包括：

- 规则集哈希
- 修订号与回合阶段
- 按坐标排序的地块
- 按稳定 ID 排序的玩家、角色和组件
- 地块池顺序与随机状态
- 分数、待处理选择和终局状态

诊断时间、动画状态、连接 ID 和日志文本不得进入指纹。

## 15. 规则错误

建议基础错误码：

- `RULE_WRONG_PHASE`
- `RULE_NOT_ACTIVE_SEAT`
- `RULE_STALE_REVISION`
- `RULE_TILE_NOT_CURRENT`
- `RULE_TILE_POSITION_OCCUPIED`
- `RULE_TILE_EDGES_MISMATCH`
- `RULE_TILE_PLACEMENT_FORBIDDEN`
- `RULE_PIECE_NOT_AVAILABLE`
- `RULE_PIECE_ZONE_INVALID`
- `RULE_FEATURE_OCCUPIED`
- `RULE_CHOICE_INVALID`

错误负载可以包含安全的结构化解释，但不能泄漏未来地块或私人状态。

## 16. 测试层级

### 16.1 单元测试

- 旋转和端口映射
- 区域图连接
- 完成检测
- 控制权和每种计分器
- 随机算法测试向量

### 16.2 官方场景测试

每个官方示例保存：

- 规则来源和页码
- 初始状态或动作列表
- 预期合法动作
- 预期计分明细
- 预期角色归还和最终状态

### 16.3 性质测试

- 拒绝命令不改变指纹
- 地块实例不会重复出现
- 每个地图坐标最多一个普通地块占用
- 分数变化等于计分事件之和
- 归还角色不再属于地图区域
- 合法动作提交后不会被同一规则版本拒绝

### 16.4 回放测试

- 同一日志运行至少多次得到相同终局指纹。
- 从不同快照点恢复得到相同终局指纹。
- Windows、WSL2 和 CI Linux 构建得到相同指纹。

## 17. 首个规则垂直切片

只实现足以验证架构的最小内容：

1. 固定少量测试地块定义。
2. 两名玩家。
3. 地块合法放置和旋转。
4. 道路和城市连接。
5. 普通随从放置。
6. 一个完成道路和一个完成城市的计分。
7. 事件保存、重放和状态指纹。

该切片不声称已经完成官方基础游戏，只用于验证规则架构。
