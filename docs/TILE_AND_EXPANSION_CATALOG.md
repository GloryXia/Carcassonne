# 地块与扩展目录

- 文档版本：0.1
- 状态：目录骨架与当前产品线清单
- 目标：建立可以逐块核验、逐扩展启用的规则资产目录

本文件不把“知道扩展大致怎么玩”视为完成。每一块地块、标记、角色和规则触发器都必须具有可追踪的数据记录、官方来源和测试用例。

## 1. 版本策略

### 1.1 默认规则族

- 当前基础版规则与视觉世代
- 2025 年修订的十大主要扩展
- 与当前基础版兼容的当前小扩展

### 1.2 历史规则

旧版扩展与 2025 修订版可能存在组件、名称、计分和回合机制差异。旧版内容必须使用独立的规则版本 ID，例如：

- `base-current`
- `expansion-01-2025`
- `expansion-01-legacy`

不得因为扩展名称相似就共享规则实现或地块数据。

## 2. 组件分类

### 2.1 地形地块

- 普通方形地块
- 起始地块
- 河流地块
- 双格或其他多格地块
- 三角形半格地块
- 固定地图或特殊布局地块
- 仅替换基础组件、不加入抽取池的地块

### 2.2 区域与地貌

- 田野
- 道路
- 城市
- 修道院
- 花园
- 河流、源头和湖泊
- 扩展定义的特殊区域

### 2.3 计分修饰与触发标志

- 盾徽
- 旅店
- 主教座堂
- 商品
- 葡萄园
- 鹅群（是否属于当前扩展 9 的正式组件及其术语待核验）
- 龙、魔法门、围城等扩展标志

### 2.4 玩家组件

- 普通随从
- 修道院长
- 大随从
- 建筑师、猪、牧羊人等特殊角色
- 玩家专属标记、纹章或资源

### 2.5 中立组件

- 龙、仙女
- 帐篷、投石机等共享单位
- 羊群、狼、商品、奖品等随机或公共标记
- 扩展专属牌堆、袋子或公共供应

## 3. 地块数据记录

每种地块至少包含以下字段：

| 字段 | 说明 |
|---|---|
| `tileDefinitionId` | 跨存档稳定的地块定义 ID |
| `rulesetVersion` | 对应规则版本 |
| `expansionId` | 所属基础包或扩展 |
| `copiesInPool` | 该图案在指定地块池中的数量 |
| `footprint` | 占用一个、多格或半格地图位置 |
| `allowedRotations` | 允许的旋转以及等价旋转 |
| `edgePorts` | 每条外边缘的地貌端口 |
| `internalGraph` | 地块内部道路、城市、田野等区域的连通图 |
| `placementConstraints` | 河流回折、特殊起始方式等额外限制 |
| `meepleZones` | 可以选择的角色放置区域 |
| `symbols` | 盾徽、商品、旅店、葡萄园等标志 |
| `triggers` | 放置、连接、完成或终局时触发的效果 |
| `scoringModifiers` | 对基础计分的修正 |
| `visualAssetId` | 3D 模型、材质和表现变体引用 |
| `sourceReference` | 官方规则页码、图例或组件表 |
| `verificationStatus` | 待录入、已录入、已复核、已测试 |

视觉模型可以更新，`tileDefinitionId`、拓扑和规则含义不得因此改变。

## 4. 基础组件目录

当前基础盒的产品清单包括：

- 72 块普通地形地块，其中包含起始地块
- 12 块河流地块
- 40 个普通随从，5 种颜色
- 5 个修道院长
- 计分板

### 4.1 基础地块规则标签

每块基础地块需要标记：

- 四边属于田野、道路、城市或河流中的哪一种
- 道路端口在地块内部如何连接
- 城市段在地块内部是否属于同一城市
- 田野段被道路和城市分隔后的连通关系
- 是否包含修道院、花园或盾徽
- 道路是否在村庄、城市、修道院或其他终点结束
- 合法角色区域及其选择碰撞范围

### 4.2 逐块清点状态

当前尚未把 72 块基础地块逐块编号并录入。正式实现规则引擎前，必须从锁定版本的官方组件表完成以下工作：

1. 为每种地块图案分配稳定 ID。
2. 记录地块池中的重复数量。
3. 录入四边端口和内部区域图。
4. 由第二次独立检查复核田野连通。
5. 为每种旋转生成合法性测试。
6. 将官方规则示例转换成场景测试。

## 8. 扩展兼容记录

每个扩展需要维护：

| 项目 | 必须回答的问题 |
|---|---|
| 依赖 | 是否需要基础模块、河流、修道院长或其他扩展？ |
| 人数 | 该扩展在当前版本支持多少玩家？ |
| 准备 | 加入哪些地块、角色、标记和公共供应？ |
| 回合顺序 | 效果插入抽取、放置、角色或计分的哪个阶段？ |
| 同时触发 | 与其他效果同时发生时按什么顺序结算？ |
| 区域拓扑 | 是否新增边缘、跨层连接或特殊区域？ |
| 力量 | 是否改变控制权计算？ |
| 计分 | 是否改变完成、最终或田野计分？ |
| 隐私 | 是否存在秘密信息或同时选择？ |
| 随机 | 是否增加独立牌堆、袋抽或随机移动？ |
| AI | AI 需要新增哪些动作和评估？ |
| 交互 | 手机和大屏如何表达选择与结果？ |
| 兼容 | 官方是否明确支持与其他扩展组合？ |
| 测试 | 官方示例、边界场景和组合场景是否通过？ |

## 9. 扩展启用等级

- **目录级**：已登记名称、版本、人数和官方来源。
- **规则级**：已完成组件清点和完整规则转写。
- **实现级**：规则模块、交互和持久化已经完成。
- **验证级**：官方示例、边界测试和确定性回放全部通过。
- **认证组合**：与指定扩展组合经过兼容测试，可以出现在正式房间中。

只有达到验证级的扩展才能提供给普通玩家。仅达到实现级的模块只能进入开发者测试房。

## 10. 完成一个扩展的定义

1. 锁定官方版本与来源。
2. 录入所有组件和准确数量。
3. 逐块录入地块拓扑与特殊符号。
4. 记录完整回合阶段和结算优先级。
5. 编写手机端所有选择流程。
6. 编写计分解释模板。
7. 实现 AI 合法动作接口。
8. 通过官方示例和独立边界测试。
9. 通过断线恢复和录像重放测试。
10. 更新兼容矩阵并明确允许的房间组合。
